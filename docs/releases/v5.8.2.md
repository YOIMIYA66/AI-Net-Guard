## AI-Net-Guard v5.8.2 发布说明 (Release Notes)

安全修复版：针对第三方审查提出的 6 条问题，重写 STUN/TURN 路由守卫（B1）的写入路径与判定逻辑，并把原先从未在真机上跑过的 **Restore → Apply 闭环**补成实测证据。防护范围与 v5.8.1 一致，未放宽任何阻断。

### 一、P0：删除 `-Force` 这个“绕过开关”

`-Force` 原本能同时跳过两道数据完整性闸门：

- **非空 `guiNDB.db-wal`**：最新路由事务可能只存在于 sidecar 里，此时复制 `guiNDB.db` 会静默丢掉它们；
- **v2rayN / 核心仍在运行**：它把路由集持在内存中，退出时整体写回数据库，任何在它之下的写入都会被丢弃。

这两条不是偏好而是正确性约束，加个开关就等于“脚本保护你的路由表——除非你赶时间”。本版**参数整体删除**，两个位置无条件拒绝。而且 WAL 检查被**前移到任何 sqlite 连接之前**：实测只要 sqlite 打开过该库，残留的 `-wal` 就会被删掉，检查放在读库之后等于死代码。

### 二、P0：`-RoutingId` 原先只管读，不管写

旧版 `dump` 会按 `-RoutingId` 读，`apply` 却重新用 `IsActive` 选一遍——中间 `IsActive` 一变，就会改错规则集。

现在所有操作（`dump` / `apply` / `compare` / `restore`）共用同一个 `pick(rows)`：显式 `--routing-id` → `IsActive=1` 唯一 → 否则报 `AMBIGUOUS` / `ID_NOT_FOUND`。解析出的 Id 贯穿后续每一次调用，`compare` 还会断言两侧是同一 Id（否则 `BACKUP_OTHER_ITEM`）。被检查的那一行，就是被写入的那一行。

顺带修掉一个坑：Python 侧选项改为**具名参数**（`--routing-id` / `--backup` / `--mode`）。PowerShell splat 会丢弃空字符串参数，位置式尾参会让值整体左移一位。

### 三、P0：遮蔽判定原先只看“字段是否存在”

旧版判 `SHADOWED` 只问“规则里有没有 port / domain 字段”，于是 `{"inboundTag":["tun"]}` 这种**没有端口限定**的规则被当成“不影响 STUN”——反例成立。

现在 `Get-StunRuleEffect` 按**探针的真实形态**求值，输出三态：

| 结果 | 含义 |
| --- | --- |
| `excluded` | 确实不可能匹配 STUN：domain 对 IP 目标不匹配 / port 集无交集 / inboundTag 非 TUN 入站 |
| `matches` | 会命中任意 STUN 探针 → 报 `SHADOWED`，计 FAIL |
| `restricted` | 有 process / source 限定，只覆盖特定来源 → 报 caveat |

TUN 标签从 `inbounds` 实读，不硬编码 `tun-in`。用户给的反例已作为固定测试用例（判 `matches`）。

### 四、P1：两脚本校验口径统一 + 纯端口语义检查

新增共用库 `scripts/lib-stun-guard.ps1`，由 `18-route-stun-guard.ps1` 与 `verify-leak-test.ps1` 同时 dot-source（缺失即 `exit 1`）。口径不一致时，“脚本说通过”就没有意义。

新增 `Test-StunPortBlockRule`：拒绝任何**收窄字段**（domain / ip / process / inboundTag / protocol / sourcePort / user）以及 `enabled=false`。B1 的语义是“按目标端口阻断，不限目标”，一条带了 domain 限定的“守卫”其实不守卫任何东西。

### 五、P1：Restore 补上现场快照与 sidecar 断言

- **恢复前先快照**到 `backup\v2rayn-restore-pre\<stamp>\`（独立树，避免“取最新干净备份”形成回环），并比对快照 SHA-256 与 live 库一致；
- **恢复后**比对整库 SHA-256 与备份，并逐规则比对内容；
- **新增 sidecar 残留断言**：恢复后若存在非空 `-wal` / `-journal` / `-shm`，`exit 3` 并给出删除命令与快照路径。该断言刻意放在**所有 sqlite 调用之后**，否则会被自己的连接清掉、掩盖证据。

### 六、P1：不让 `Shadow=0` 被读成“全清”

`verdict: B1 ACTIVE` 现在强制带 caveat 计数与明文限定：

```
verdict: B1 ACTIVE - both rules loaded, every port in the configured STUN/TURN
         set is dropped inside the core for ALL destinations, foreign included.
         caveat: 1 rule(s) above are origin-scoped and were NOT ruled out.
         ... ACTIVE means "nothing here matches an arbitrary STUN probe", not "all clear".
```

`RESULT:` 汇总行同样带 caveat 计数。

### 七、真机闭环实测（本版新增的证据）

在真实 v2rayN 库上完整跑通 `Apply → 重启 → Verify → Restore → Apply → 重启 → Verify`：

| 环节 | 结果 |
| --- | --- |
| `-Apply` | 11 条，guard 位于 index 0/1，其余 9 条内容未变，`exit 0` |
| 内核加载 | `config.json` 中 guard 落 **routing index 5/6**，12 端口全集 udp+tcp |
| `-Restore` | live 库 SHA-256 `498798fc…f1744bc9` 与备份**逐字节一致**，回到 9 条，`quick_check ok`，无 sidecar |
| 再次 `-Apply` | 库 SHA-256 `36b171fd…e97afc`，**与首次 Apply 后的副本完全相同** |
| STUN 探针 | miwifi / bilibili / qq / google / cloudflare **5/5 全部静默** |
| 隔离测试（5 条 WFP UDP 规则全关，只留 B1） | **5/5 仍静默** → 包确实在核心内被丢弃，不是 NIC 规则造成的假象 |

那个 `36b171fd…` 是本版最有说服力的一条：两次独立 Apply、中间隔着一次完整回滚，产出**字节级相同**，说明链路是确定性的，不是“碰巧规则内容一样”。

### 必须披露的三点

1. **`B1 ACTIVE with 1 caveat`**：guard 之前第 3 条规则是 `out=direct, process=xray/sing-box/self`，它没有端口与域限定，只是被 process 收窄。**核心自身**发起的 STUN 不在守卫范围内。因此拒绝写成“前置规则已全部排除干扰”。
2. **范围限定**：守卫只覆盖 12 个端口（3478 / 3479 / 5349 / 5350 / 19302-19309）的 udp + tcp，且对所有目标生效（境外同样阻断，没有为了通过测试放开）。STUN/TURN 走 udp/443 等非标端口不在范围内，WebRTC 通话可能退化为中继或失败——这是 B1 的既定取舍，不是缺陷。
3. **归因边界（本版新增披露，且已实测澄清）**：探针静默**不能**直接推出“包在核心内被丢弃”。同一时刻生效的还有 WFP 层的 `AI-Guard-Block-WebRTC-UDP`（program=Any，同 12 端口，Outbound Block）等规则，它同样能造成静默。

   本版因此补做了一次隔离测试（提权终端，`backup\tools\probe-stun-isolated.ps1`）：临时禁用全部 5 条 Outbound UDP 规则（`AI-Guard-Block-WebRTC-UDP` / `-LocalIP-UDP` / `-xray-CoreSTUN-UDP` / `-Chrome-PhysUDP` / `-Edge-PhysUDP`），保留 B1 与 TUN，然后重打同样的 5 个 UDP STUN 探针。

   结果：**5/5 仍然静默**（2500 ms 内无任何数据报），测试后 5 条规则全部恢复为 `Enabled=True`。WFP 层被完全移除后唯一剩余的阻断层就是核心，因此 **B1 确实在核心内丢弃 TUN 转发的 STUN**，此前的静默不是 NIC 规则造成的假象。

   原始输出（提权终端，节选）：

   ```
   core config : guard pair present (block, 12-port set, udp + tcp)
   state before:
   AI-Guard-Block-WebRTC-UDP                      True
   AI-Guard-Block-WebRTC-LocalIP-UDP              True
   AI-Guard-Block-WebRTC-xray-CoreSTUN-UDP        True
   AI-Guard-Block-WebRTC-Chrome-PhysUDP           True
   AI-Guard-Block-WebRTC-Edge-PhysUDP             True
   [+] disabled 5 outbound UDP rule(s); the B1 pair is untouched
   --- probes (any reply at all is a failure) ---
   [SILENT] miwifi (CN) -> no datagram within 2500 ms
   [SILENT] bilibili (CN) -> no datagram within 2500 ms
   [SILENT] qq (CN) -> no datagram within 2500 ms
   [SILENT] google (foreign) -> no datagram within 2500 ms
   [SILENT] cloudflare (fw) -> no datagram within 2500 ms
   [+] re-enabled 5 rule(s)
   state after:  (all five back to True, no MISMATCH)
   VERDICT: B1 DROPS STUN IN THE CORE
   ```

   这次测试还顺带缩小了前面那条 `process: xray/` 的 caveat 的适用范围，但**只覆盖了一半**，两个命题必须分开说：

   | 命题 | 当前证据 |
   | --- | --- |
   | TUN 转发的 STUN 探针没有被 process-scoped direct 规则接走 | 隔离测试强力支持：若被接走，包会经物理网卡直出，而当时 WFP 已关闭，必然收到回复；实测零回复 |
   | 核心自身发起的任何 STUN 都不可能命中该 direct 规则 | **尚未直接测试**，不能由这 5 个探针推出 |

   准确表述是：**TUN 转发路径已验证**，B1 能在核心内丢弃指定端口的 STUN；**核心自身发起的流量**仍受该 process-scoped 规则约束，但当前配置的 outbounds 只有 `vless / freedom / blackhole / dns`，未发现会主动产生 STUN/TURN 的核心功能，因此尚无实际触发证据。这条 caveat 保留为**配置边界说明**，不作为已排除处理。

   尽管如此，`verify-leak-test.ps1` 仍保留 `ATTRIBUTION` 提示行：这个结论来自一次单独执行的隔离测试，每次运行无法自动得出，把它写成常驻结论就会重复本版要修的毛病。**因此常规验收结论仍是 `PASSED WITH CAVEAT`，不是“无泄漏”。**

实际输出已按此收紧：

```
RESULT: PASSED WITH CAVEAT
        all 5 configured STUN endpoints were silent during this test.
        both B1 guard rules were loaded and the complete configured
        12-port UDP/TCP set was present.
        CAVEAT: an origin-scoped direct rule precedes the guard.
                traffic matching that rule may bypass B1.
        SCOPE : non-standard STUN/TURN ports, including udp/443,
                are outside this guard.
        ATTRIBUTION: silence does not by itself prove a core-side drop -
                the physical-NIC STUN rules block the same egress.
```

补充事实：当前核心配置的 outbounds 只有 `vless / freedom / blackhole / dns` 四种，**没有任何 STUN/TURN 出站**，因此“核心自发 STUN”在当前配置下不存在可达路径。另有一条 `AI-Guard-Block-WebRTC-xray-CoreSTUN-UDP/TCP` 规则（program = xray.exe 全路径，同 12 端口，Outbound Block）作为该场景的独立兜底。

### 升级提示

若已按 v5.8.1 同步过生产目录，本版需重新同步脚本（提权终端）：

```powershell
.\13-harden-acl.ps1 -Root "C:\AI-Net-Guard" -SyncWorkspace -WorkspaceRoot <repo> -SkipVerification
```

改用 B1 守卫前，**先退出 v2rayN**（托盘右键退出，不是点 ×），否则 `-Apply` 会拒绝执行——这是设计行为，不是故障。
